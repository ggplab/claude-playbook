# run-hackathon

해커톤 하루를 **기획, 개발, 검증, 영상 녹화, 발표** 다섯 단계로 돌리는 꾸러미다. 앞에 0단계(규정, 심사 기준, 마감 읽기와 세션 나누기), 뒤에 제출 체크리스트와 회고를 둔다. 단계마다 무엇을 하고, 어느 세션이 맡고, 무엇으로 끝났다고 판정하는지 적었다.

근거는 2026-10-16 행사의 공유 노트, 덱과 대본 초안, 앱 README, 블로그 초안이다. 재료에 없는 것은 "미확인", 계획만 있고 실행 기록이 없는 것은 "계획"으로 적었다. 사내 해커톤과 데모데이도 같은 순서로 돈다. 0단계의 행사 자원(계정 삭제 시각, 크레딧)을 그 행사의 규정(외부 서비스 사용 허용 범위, 데이터 반출)으로 바꿔 읽는다.

## 0. 규정, 심사 기준, 마감 읽기와 세션 나누기

**하는 일**

- 행사 가이드에서 마감 시각, 심사 기준, 제출 형식, 사전 제작 조항, 발표 형식을 한 줄씩 노트에 옮기고 역산 일정을 만든다. 이날 확인된 시각: 덱과 대본 동결 14:30, 제출 15:00, Top 4 데모 발표 16:00, 행사 계정 삭제 17:00 무렵, 시청회 22:00.
- 심사 기준 중 재료로 확인된 것: 심사는 발표자료가 아니라 작동하는 데모로 한다(블로그 초안), 심사 항목 "Argon이라서 가능한가"(어디에 어떤 모델을 썼는지 한 장으로 보인다), 데모는 실제 입력으로 에러 없이 돈다.
- **미확인**: 규정 원문의 사전 제작 조항, Top 4 발표 형식(가이드에 16:00~16:30 Top 4 데모 발표만 있고 시간 제한 없음), 실제 제출 형식(대본은 Drive 링크로 낼 계획이었으나 실제 제출 기록 없음). 다음 행사에서는 원문을 읽고 시각표 옆에 적는다.
- 행사 도구, 프로젝트 ID, 리전, 지급 크레딧을 적는다. 행사 도구가 **개인 로그인에서 어떤 모델을 쓰는지** 먼저 돌려 본다. 이날 agy CLI는 개인 로그인에서 Argon을 쓸 수 없어 기본 모델이 Gemini 3.8 Flash였다(2026-10-16 실측).
- 세션을 나누고 공유 노트 폴더 규약을 만든다(아래).

**공유 노트 규약(이날 쓴 것)**

- 한 폴더에 `<세션>-<주제>.md`로 쓴다. 예: `app-build-status.md`, `app-architecture.md`, `deck-and-recording.md`, `korean-posts.md`.
- 파일 맨 위에 시각과 작성 세션을 적는다. 결정 요청은 선택지에 번호(A, B, C)를 붙여 쓰고, 답한 쪽은 같은 번호로 답한다(`deck-story-review-request.md`와 `-answer.md`).
- 사용자 결정은 원문을 그대로 옮긴다(`app-build-port-sync.md`: "만들고 데모 만들자. 그리고 코드는 이식해. 필요한 건 내가 책임질게.").
- 확인한 사실과 추정을 나눠 적는다. 덱 세션의 "미확인:" 줄이 그 예다.

**맡는 세션**: 메인.

**완료 판정**: 마감 시각표 노트가 있고, 미확인 항목이 따로 적혀 있다. 모든 보조 세션의 첫 지시에 노트 폴더 경로와 규약 한 줄이 들어 있고, 메인이 노트만 읽고 각 세션의 상태를 말할 수 있다.

## 1. 기획

### 1-1. 모델 설계 (기획의 맨 앞)

제품 기능보다 모델을 먼저 본다. 주최 측이 대표 모델을 내건 해커톤은 심사도 그 모델을 얼마나 제대로 썼는지를 본다. 2026-10-16 회고의 결론이다.

1. **대표 모델의 강점을 심사 기준 문구에서 뽑는다.** 규정·심사 기준·행사 안내에 적힌 표현을 그대로 옮겨 목록을 만든다. 예: 1M 컨텍스트, 긴 디코드, 최첨단 추론, 멀티모달 오케스트레이션, Managed Agents, 검증 루프. 그다음 "그 모델이 아니면 안 되는 일"부터 제품 기능을 설계한다. 다른 모델로도 되는 기능은 뒤로 미룬다.
2. **기능별 모델 표를 사전 조사로 만든다.** 열은 기능, 맡길 모델이나 에이전트, 이유, 그 모델의 기능과 한계(입력 크기, 속도, 비용, 영상·음성 지원), 예상 호출 수다. 한계 칸은 제공사 공식 문서로 확인하고, 확인하지 못한 칸은 "미확인"으로 둔다. 큰 모델은 판정처럼 적게 부르는 자리에 두고, 대량 처리는 가벼운 모델이 먼저 맡는다.
3. **시작 전 점검.** 개발을 시작하기 전에 아래 세 가지를 확인한다.
   - 코딩 에이전트(agy 등)를 **행사 계정과 프로젝트 ID**로 로그인하고, 모델 목록에 대표 모델이 있는지 본다. 이날은 개인 로그인으로 agy를 써서 목록에 대표 모델(gemini-4-argon)이 없었고, 기본 모델(Gemini 3.8 Flash)로 돌았다(2026-10-16 실측).
   - 화면 없는 실행(`-p`)에서 파일 쓰기 승인이 어떻게 되는지 확인한다. 이날 오전 agy `-p`는 승인 문제로 파일을 쓰지 못했다.
   - 결제는 선불 API 키가 아니라 **프로젝트 결제(Vertex AI)**로 잡는다. 이날 행사 AI Studio 키는 크레딧이 바닥났고, 배포본은 Vertex AI 서비스 계정으로 호출했다.

**완료 판정**: 대표 모델 강점 목록(출처 문구 포함), 기능별 모델 표(한계 칸 출처 또는 "미확인"), 시작 전 점검 세 항목의 결과(모델 목록 출력, 쓰기 시험 결과, 결제 방식)가 기획서에 있다.

### 1-2. 문제와 포지션

이날 하루를 기획 70, 발표 20, 개발 10으로 나눴다(블로그 초안). 코드를 오래 붙잡는 것보다 문제를 정확히 잡는 쪽이 결과를 더 많이 바꾼다고 봤다.

**하는 일**

- **인터뷰**: 미래를 묻지 않고 최근에 실제로 있었던 일을 묻는다. 한 사람 10~15분, 녹음 동의와 인용 허락을 먼저 받고 발표에는 이름 대신 "독서모임 멤버 A"로 쓴다(`watch-party-interview.md`). 요지만 옮긴 말은 직접 인용이 아니므로 SNS에 싣기 전에 인용 허락을 다시 받는다. 이날 방향을 가장 크게 바꾼 것은 아침 인터뷰였다. 스포일러만 막는 도구에서 늦게 온 사람이 나가지 않게 하는 도구로 넓혔다.
- **경쟁 조사**: 조사는 다른 모델(GPT, Gemini)에 맡기고 출처를 붙여 받는다. 출처가 없는 주장은 발표에서 뺀다. 결과는 비교표(O, X, △)로 만들고, 공식 원문을 못 본 칸은 △나 각주로 낮춘다. 이날 SOOP의 중간 입장 요약이 나와 차별점 문장을 다시 썼다("되감기 대신 요약"만으로는 약함).
- **포지션과 차별점 한 줄**을 기획서에 적는다. 이날: "채팅을 쓴 시각이 아니라, 채팅이 말하는 장면으로 연다. 요약과 답변도 당신이 본 지점까지만."
- **이름**을 기획 단계에서 정한다. 이날은 이름을 미리 정할 생각을 하지 못했다(블로그 초안).
- **사전 제작물 처리**: 전날 만든 프로토타입을 이식하면 숨기지 않고 README와 소개글에 한 줄로 밝힌다. 이날 사용자가 위험을 직접 감수하기로 결정했다. 규정상 허용되는지는 **미확인**.

**맡는 세션**: 메인(기획서, 결정), 다른 모델(조사).

**완료 판정**: 1-1의 판정을 통과했고, 기획서에 한 줄 포지션, 차별점 한 줄, 이름이 있고, 비교표의 모든 칸에 근거 경로나 각주가 있으며, 사용자가 기획서와 사전 제작물 처리를 확정했다.

## 2. 개발

**하는 일**

- 구조: 백엔드 한 서비스(FastAPI, Docker 이미지 하나), 모델은 Vertex AI에서 Cloud Run 서비스 계정으로 호출(API 키 없음), 저장은 `DATA_DIR`의 JSON. 행사 키가 401이면 서비스 계정 경로로 간다.
- 코드는 Claude Code가 쓰고 화면 이식은 Sonnet 서브에이전트에 맡겼다(app-architecture.md). 제품 안 AI는 Gemini다(장면 기록 gemini-4-argon, 질문 답변 gemini-3.8-flash, 채팅 가림 gemini-3.5-flash-lite, README 표).
- 배포: Cloud Run, 리전 `asia-northeast3`. README의 배포 명령은 `gcloud run deploy`다. gcloud가 막히면 현장 안내대로 Antigravity나 agy에서 Cloud Run MCP로 "이 폴더를 Cloud Run에 배포. Project ID, Region, Service Name" 형식으로 시킨다(현장 튜토리얼 화면 기준, 이날 이 경로를 실제로 썼는지는 미확인).
- 리비전 관리: 새 리비전을 올리고도 트래픽을 옮기지 않을 수 있다. 이날은 온보딩 투어 버전(00015)을 트래픽 0%로 두고 녹화와 심사용 00014를 100%로 고정했다. 명령은 `gcloud run services update-traffic <서비스> --region asia-northeast3 --to-revisions <리비전>=100`.
- 데모 모드: 시청자 시각 고정, 대본 채팅, 정확히 같은 키(영상, 질문, t, 기록 버전)의 답변 캐시(15초를 넘으면 캐시만 재생). 기능마다 클릭 한 번에 한 가지가 보이게 하고, 녹화 가능한 상태로 동결한다(이날 목표 14:00).
- 사람 확인 단계와 모델 사용처 표(어디에 어떤 모델, 호출 수, 지연)를 `/score` 같은 공개 엔드포인트와 README에 남긴다.
- 백업: 행사 계정은 행사 뒤 사라진다. 같은 이미지를 상시 장비(이날은 맥미니 Docker + Cloudflare Tunnel)에 올리고, 장면 기록처럼 컨테이너 밖에 없는 데이터를 로컬에 내려받는다.

**맡는 세션**: 앱 개발.

**완료 판정**: 서비스가 서빙 중인 리비전 이름을 확인했고(커밋이 아니라 리비전으로 판정), 데모 URL을 새 탭에서 열어 클릭 한 번씩으로 각 기능이 보이며, 백업 장비에서 같은 이미지가 뜬다.

## 3. 검증

만든 쪽이 아닌 눈으로, 숫자와 정답지로 확인한다. 검증 결과는 발표와 소개글의 숫자가 된다. 완료 판정을 하나라도 통과하지 못하면 2단계로 돌아가 고친 뒤 다시 잰다.

**3-1. 제품 안 검증 루프**

- 큰 모델이 쓴 기록을 가벼운 모델이 표본으로 다시 확인하고, 엇갈리면 큰 모델이 다시 보고 유지나 수정을 정한다. 이날: 5분 구간마다 무작위 3장면을 gemini-3.8-flash가 그 클립을 다시 보고 화면 글자, 팀 정보를 비교, 모순이면 gemini-4-argon이 다시 판단(구간당 상한 2회).
- 이날 숫자(1화 0~30분): 장면 102개, 16곳 확인, 6곳 불일치, Argon 유지 5, 수정 1. 결과는 `/score`로 공개했다.
- 완료 판정: 확인 수, 불일치 수, 유지, 수정이 `/score`나 로그에 남아 있다.

**3-2. 정답지 대조**

- 판정형 기능(이날은 채팅 스포일러 가림)은 사람이 먼저 정답지를 만들고 모델 판정과 대조한다. 이날: 데모 채팅 12줄의 가림 판정이 정답지와 일치(앱 개발 세션 보고).
- 비교 측정이 있으면 어느 날 어떤 세트로 쟀는지 붙여 쓴다. 18/18 가림, 안전한 채팅 Argon 기록 21/22, 자막만 17/22는 **행사 전날(2026-10-15) 시험 세트** 결과다. 당일 재측정 여부는 미확인.
- 완료 판정: 정답지 파일과 대조 결과(일치 수/전체)가 있고, 숫자마다 측정 날짜와 세트가 적혀 있다.

**3-3. 다른 모델 교차 검토**

- 만든 모델과 다른 모델에 산출물을 보여 준다. 이날 gemini-4-argon이 앱 스크린샷을 보고 영향도 순 UI 문제 7개와 유지할 점 3개를 냈다(`argon-ui-review.md`).
- 발표 스토리는 덱 세션이 결정 요청(A~G)을 노트로 올리고 메인이 기획서 근거로 답했다. 같은 Claude 세션끼리의 검토이며, 이 과정에서 비교표 판정이 바뀌었다(SOOP X를 △로, 각주 추가).
- 완료 판정: 검토 결과 파일이 있고, 반영한 것과 반영하지 않은 것이 결정 노트에 적혀 있다.

**3-4. 주장 검증**

- 모델 사용처 표는 기획 노트가 아니라 코드에서 다시 만든다. 이날 `app/main.py`를 읽어 모델 ID와 호출 경로를 확인했다.
- 측정하지 않은 주장은 싣지 않는다. 이날 뺀 것: "Argon이 화면 질문에서 자막보다 낫다", 번아웃 해결, "어느 플랫폼에도 없는 기능".
- 코드를 쓴 도구와 제품 안에서 쓴 모델을 섞어 쓰지 않는다. 초기 노트가 코드 작성 도구를 Argon으로 적었고, 코드와 README로 Claude Code임을 확인해 바로잡았다.
- 대외 문구 검사: em dash와 가운데점 `grep -nP "[\x{2014}\x{00B7}]"` 0건.
- 완료 판정: 덱, README, 소개글의 숫자와 모델 이름이 코드와 `/score` 값과 같고, 문구 검사 grep이 0건이다.

**3-5. 배포본 실측**

- `curl -sf <배포URL>/health` 200, 서빙 중인 리비전 이름, 기능별 지연을 잰다. 이날: 따라잡기 4~12초, 가림 판정 약 2초.
- 리비전 캐시를 피하려고 새 탭이나 시크릿 창으로 열고, 첫 요청이 느리므로 따라잡기를 한 번 눌러 서버를 깨운다.
- 완료 판정: 위 세 값이 노트에 있고, 녹화와 심사에 쓸 리비전이 트래픽 100%다.

## 4. 영상 녹화

**하는 일**

- 대본은 장면별 표(시간, 화면, 내레이션, 단어 수)로 쓰고, 초당 2.5단어를 넘지 않게 한다. 데모의 주인공은 사용자 경험이고 점수판은 마지막 20초만 쓴다.

- 앱 상태: 새 탭이나 시크릿 창으로 열고, 따라잡기는 한 번 눌러 서버를 깨운 뒤 녹화한다.
- 대본 채팅은 "시연용으로 미리 쓴 대본"이라고 화면이나 내레이션에서 밝힌다. 오류를 일부러 넣어 교정을 보여 주면 반드시 그렇게 말한다(대본 규칙, 이날 실제 촬영 여부는 미확인).

- SNS 비율: LinkedIn 일반 피드는 비율 1:2.4~2.4:1까지 공식 확인, Threads는 공식 도움말에서 **미확인**. 이날은 4:5를 기본으로 정했다.

**맡는 세션**: 덱과 녹화. 녹화 버튼과 내레이션은 사람이 한다.

**완료 판정**: `ffprobe -v error -show_entries format=duration -of csv=p=0 <파일>`이 제한(이날 180초) 이하, 화면에 키, 이메일, 실명이 없음, 무음 원본과 편집 프로젝트 파일이 보관되어 있다.

## 부록. screentour 사용

```bash
cd ~/.claude/skills/run-hackathon
uv run --with playwright==1.56.0 python scripts/screentour.py examples/watch-party.json --out out/ [--lang ko]
```

- playwright 버전은 저자 환경에 설치된 chromium 빌드에 맞춰 1.56.0으로 고정했다. 버전이 다르면 "Executable doesn't exist"가 나온다. 이 경우 버전을 맞추거나 `playwright install`을 실행한다.
- 입력 JSON: `url` 또는 `image`, `viewport`, `pre`(클릭, 대기, 숨김 단계), `items[]`(selector 또는 box, `title_en/ko`, `caption_en/ko`, `side`). 필드 설명은 스크립트 상단 docstring.
- 출력: `out/tour-01.png`부터 장마다 1장, 덱에 붙일 `out/tour.html`, 원본 캡처 `out/capture.png`. 모양은 덱의 화면 둘러보기 장(60px 옅은 그리드, 빨간 박스, 박스 밖 어둡게, 빨간 말풍선)을 따른다.
- selector를 못 찾으면 항목 이름과 함께 멈춘다. 데모 모드는 방송 시계가 흐르고 채팅이 시간에 따라 나오므로 `pre`의 `wait_for`로 장면이 나타날 때까지 기다린다(예: `#log .msg.locked`). Cloud Run 첫 요청이 느리므로 `goto_timeout_ms`를 넉넉히 둔다.
- 행사 URL이 사라진 뒤에는 `examples/watch-party-capture.png`를 `image`로 받는 `examples/watch-party-image.json`(box 좌표 직접 입력)으로 같은 3장을 다시 만든다.
- 알려진 차이: 이 예시를 뽑은 시점의 배포본은 스포일러 채팅이 흐림이 아니라 "Spoiler (a later scene), click to show" 줄로 나온다. 덱 14장의 "blurred" 문구와 화면이 다르면 문구나 캡처를 맞춘다.
