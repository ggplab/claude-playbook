# brunch-apply: 브런치 작가 신청서 준비

> **주의: 이 스킬의 문안과 샘플 글은 참고용 초안이다.** 브런치는 에이전트가 쓴 글을 걸러내는 것으로 보인다(2026-09 저자 주변에서 글 8편이 막힌 사례, 공식 안내는 없음). 제출하는 소개, 활동 계획, 서랍 글은 저자가 초안을 보고 자기 문장으로 다시 쓴다. 초안을 그대로 붙여 넣지 않는다.

## 무엇을 하는 스킬인가

브런치 작가 신청은 소개 300자, 활동 계획 300자, 첨부 글, SNS 주소 네 칸이 전부다. 그런데 후기를 모아 보면 떨어지는 이유는 글솜씨가 아니라 **기획과 첨부 글의 불일치**다. 이 스킬은 그 네 칸을 한 컨셉으로 묶어 만든다. 근거 없이 문안만 뽑지 않는다. 심사 기준과 후기는 URL로 인용하고, 컨셉은 브런치 안에 이미 얼마나 있는지 실측하고, 문안의 사실은 저자 자산에서 온 것만 쓴다.

저자 실사고가 출발점이다. 1차(2026-09-17)는 육아 아빠 컨셉에 도구 칼럼을 첨부해 미선정, 2차(2026-09-18)는 같은 재료로 틀과 첨부 글만 바꿔 선정됐다(2026-09-21). 기록은 `docs/2026-09-18-brunch-writer-application.md`.

## 입력과 출력

| 입력 | 어디서 |
|---|---|
| 저자 자산 | Threads 발행본 디렉토리(`sns/published/threads/`), 블로그 글, 책, 프로젝트 파일. 사실과 표현은 여기서만 가져온다 |
| 문체 기준 | `sns/guides/writing-style.md` 「네이버 블로그」 절 (평서체, 문장 40자 안팎, 어긋난 장면, 실행 문장 마무리) |
| 이전 신청 기록 | 있으면 탈락 원인 진단부터 시작한다 |
| 인터뷰 답변 | 4단계에서 사용자에게 직접 받는다 |

| 출력 | 형식 |
|---|---|
| 신청서 문안 3종 | 작가 소개(300자 안), 활동 계획(300자 안), 목차 12편과 재료 표 |
| 서랍 글 2편 | 제목 + 본문, 머리에 사실 소스와 미확인 문장 |
| 겹침 조사표 | 주제 / 겹침 판정 / 상위 제목 예 |
| 기록 문서 | `docs/YYYY-MM-DD-brunch-writer-application.md` (`assets/record-template.md` 틀). 신청 원문, 근거, 이력을 한 파일에 둔다 |

## 절차

### 1. 이전 기록 읽기와 진단

이전 신청이 있으면 원문 네 칸을 그대로 옮겨 적고 어긋난 곳을 찾는다. 판단 순서는 넷이다. 첨부 글이 컨셉과 같은가, 소개 마지막 문장이 사람 소개인가 광고인가, 목차의 주인공이 사람인가 도구인가, 수치에 근거가 있는가. 재료(그 사람만 쓸 수 있는 경험)가 있는데 떨어졌다면 재료가 아니라 틀을 고친다. 한 번의 탈락으로 컨셉을 버리지 않는다.

### 2. 심사 기준과 후기 읽기

`references/review-criteria.md`를 읽는다. 공식 기준(https://brunch.co.kr/@brunch/2)은 출간 경험, 전문성, 이야기를 전할 준비 세 가지이고, 폼은 첨부 자료를 "가장 중요한 자료"라고 안내한다. 후기의 탈락 원인은 기획 부족, 과거 글 자랑, 홍보성, 모호한 계획 네 가지다. 새 후기를 더 찾으면 URL과 함께 그 파일에 행을 더한다. URL 없는 주장은 넣지 않는다.

### 3. 컨셉 후보와 겹침 조사

저자 자산을 훑어 연재 컨셉 후보를 2~3개 낸다. 후보마다 주제어 3개 안팎으로 브런치 안의 겹침을 잰다.

```bash
python3 .claude/skills/brunch-apply/scripts/brunch_overlap.py "주제어 1" "주제어 2" "주제어 3"
```

상위 8건 제목이 내 컨셉과 얼마나 같은지로 포화 / 많음 / 적음 / 거의 없음을 적는다. 총건수는 낱말 하나만 맞아도 세므로 판정 근거로 쓰지 않는다. "거의 없음"은 상위 8건에 없었다는 뜻이지 실제로 없다는 증거가 아니다. 포화 주제(퇴사담, 회사는 나를 책임지지 않는다 등)는 연재의 배경 한 편으로만 쓴다.

비슷한 컨셉으로 이미 작가가 된 사람이 있으면 그 글을 읽는다. 겹침이 아니라 **그 자리가 비어 있지 않다는 증거**이고, 그들이 어떤 순서로(사람이 앞, 도구가 뒤) 썼는지가 문안의 기준이 된다.

### 4. 저자 인터뷰 4문항

문안을 쓰기 전에 사용자에게 네 가지를 묻는다. 답은 기록 문서 4절에 요지로 남기고, 답에서 나온 문장은 소개와 샘플 글에 그대로 살린다.

1. 이 연재를 쓰게 된 계기
2. 기억에 남는 장면 하나 (당황했거나 틀렸던 순간이면 더 좋다)
3. 쓸 수 없는 것과 제약 (시간, 소재, 가족)
4. 공개 범위 (가족, 수입, 고객, 아이 이름과 얼굴)

샘플 글마다 사실 확인이 더 필요하면 그때 한두 문항을 더 묻는다. 지출 규모의 감각, 막힌 지점 하나처럼 소스에 없는 디테일이 대상이다.

### 5. 작가 소개 (300자)

사람 소개로 쓴다. 심사자가 읽는 것은 강사 프로필이 아니라 "이 사람은 누구이고 무엇을 쓸 것인가"다.

- 첫 문장은 장면이나 신분 한 줄. "연년생 남매를 키우는 아빠입니다."
- 청중에게 말하는 문장을 빼라. "맞벌이 부모에게 ~를 소개합니다", "~를 전하려 합니다"는 강의 안내문의 약속이라 홍보로 읽힌다. 1차와 2차 첫 수정안이 여기서 걸렸다.
- 출간과 경력은 괄호 한 줄. 공식 기준에 출간 경험이 있으니 빼지는 않되 앞세우지 않는다.
- 어긋난 장면을 하나 넣는다. 잘된 것만 나열한 소개는 광고와 구분되지 않는다.
- 세어서 확인한 수치만. "50개 기업"처럼 근거 없는 수는 삭제하거나 "수십 곳"으로 바꾼다.

### 6. 활동 계획 (300자)과 목차 12편

연재 제목을 먼저 정한다. 후보 2~3개에 근거 한 줄씩 붙여 사용자가 고른다. 소개 첫 문장을 그대로 제목으로 올리는 방식이 잘 맞았다(「아이 재우고 여는 노트북」).

활동 계획은 "연재 「제목」을 주 1회 씁니다" + 무엇을 기록하는지 두 문장 + 부별 목차다. 300자 안에 부 4개, 회차 7~8개가 들어간다. 별도로 기록 문서에 **12편 목차와 재료 표**를 둔다. 회차마다 재료(Threads 발행본 날짜와 제목, 인터뷰 답변 번호)를 적어 "몇 편 쓰면 바닥나는" 기획이 아님을 스스로 확인한다. 절반 이상은 도구가 없는 삶과 일 이야기여야 한다. 편마다 주인공이 도구이면 심사자는 "육아 이야기를 앞에 붙인 자동화 강사"를 본다.

### 7. 서랍 글 2편

옛 글을 다듬지 않고 컨셉을 대표하는 글을 새로 쓴다. 후기의 합격자들이 공통으로 한 일이고, 1차 탈락의 가장 큰 원인이 첨부 글과 컨셉의 불일치였다.

- 목차에서 소재와 결말이 가장 뚜렷한 2편을 고른다. 첫 편은 어긋난 장면과 판정이 있는 것, 둘째 편은 감정에서 시작해 완성으로 끝나는 것.
- 문체는 `sns/guides/writing-style.md` 「네이버 블로그」 절이 기준이다. 초안을 낸 뒤 그 절의 체크리스트 7개를 돌린다. Threads 원문 표현(훅훅, 뼈 맞았다, 38기가)을 그대로 살리면 사람 글로 읽힌다.
- 도구는 진단을 내리거나 실패하는 역할로만 나온다. 설명서가 되면 안 된다.
- 머리말에 사실 소스와 미확인 문장을 적는다. 소스에 없는 금액, 이름, 반응은 쓰지 않는다. 미확인 문장은 사용자가 읽고 고친다.
- 아이 이름은 쓰지 않는다. 첫째, 둘째로 부른다.
- 제출 전에는 어디에도 공개하지 않는다. 브런치 서랍에만 저장한다.

### 8. 사용자 검토

문안 3종과 샘플 2편, 겹침 조사표를 한 화면에 보여 주고 고칠 곳을 받는다. 글자 수는 폼 기준과 같은 방식으로 센다.

```bash
python3 -c "import sys; t=open(sys.argv[1]).read().strip(); print(len(t), '자')" bio.txt
grep -nP "[\x{2014}\x{2013}\x{00B7}]" sample1.txt sample2.txt   # 0줄
grep -n "<아이 이름>" sample1.txt sample2.txt                    # 0줄
```

### 9. 서랍 저장과 폼 입력 (Aside)

`references/aside-form.md`를 읽고 그대로 한다. 순서는 로그인 계정 기록, 서랍 글 2편 저장과 글자 수 대조, 폼 01 소개, 02 계획, 03 서랍 글 2편 체크와 외부 링크, 04 홈페이지 주소까지다. ref는 `aside repl` 호출마다 새 snapshot에서 다시 찾는다.

### 10. 제출 게이트 (고정)

**선택 동의 체크와 "신청서 보내기"는 스킬이 누르지 않는다.** 4단계 입력값을 표로 보여 주고 사용자 확인을 받은 뒤, 사용자가 직접 누른다. 사용자가 "눌러 줘"라고 명시하면 그때 누른다. 신청서는 보낸 뒤 고칠 수 없고, 어느 계정으로 보냈는지 모르면 접수 여부를 추적할 수 없다.

제출 직후 `brunch.co.kr/apply`의 "심사중" 화면을 캡처해 기록 문서 옆에 둔다. 결과 메일(`noreply.brunch@kakaocorp.com`, 영업일 5일 안)이 오면 제출 이력 표에 적는다.

## 완료 판정

| 단계 | 판정 |
|---|---|
| 겹침 조사 | 컨셉 후보마다 판정 열이 채워진 표가 기록 문서 3절에 있다 |
| 소개, 계획 | 로컬 글자 수 300 이하이고 폼의 "N/300"과 같다 |
| 서랍 글 | 서랍 목록에 2편, 편집기 글자 수가 파일과 같다, 아이 이름 0건, em dash 0건 |

| 제출 | 사용자가 눌렀고 "심사중" 캡처가 있다 |
| 기록 | 기록 문서에 원문, 근거 URL, 로그인 계정, 이력 표가 있다 |

## 선정 뒤

이 스킬은 신청서까지다. 선정되면 연재 원고는 `brunch/CLAUDE.md` 규칙(발행은 사람이, 편집기 입력도 사람이)을 따르고, 서랍 글 2편은 그대로 1화와 2화 초안이 된다.
